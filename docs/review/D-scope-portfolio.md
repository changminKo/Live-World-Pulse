[요약] Phase 0~5 전부는 1인·주 12h 기준 약 9~14개월로 완주 확률 낮음 — Phase 0 + 축소 Phase 1 + '지진 한정 Time Machine'에서 멈추는 것이 포트폴리오 가치 최대. Phase 순서에 치명적 위반 1건(과거 데이터 축적·백엔드 구축이 어느 Phase에도 배정 안 됨), 누락 항목 13건(테스트·배포·디자인·attribution 등 계획서에 단어 자체가 없음). 아래 전문 리포트.

## 1. 스코프 판정 + 기간 추정

**판정: 전체 스코프는 1인 사이드 프로젝트로 과대. 완주 확률 낮음.**

가정: 1인, 사이드 프로젝트 주 10~15h 투입(중간값 12h), 프론트 경력자이나 지리공간·WebGL 실전 경험은 보통 수준, 외부 API 무료 티어 사용.

| Phase | 내용 | 낙관 | 현실 | 주요 리스크 |
|---|---|---|---|---|
| 0 Prototype | Globe + 지진 + 항공기 + 토글 + 클릭 | 3주 | 4~5주 | 엔진 선택 삽질, OpenSky 무료 티어 제약(익명 크레딧 대폭 축소, 계정 필요) |
| 1 MVP | + 날씨 + 뉴스 + Timeline + Detail + URL + 클러스터링 | 6주 | 8~12주 | **뉴스 지오코딩은 그 자체로 별도 프로젝트급**. 전 지구 날씨 오버레이도 마찬가지 |
| 2 Time Machine | 백엔드 + 저장 + 수집 파이프라인 + Seek/Replay | 6주 | 8~10주 | 백엔드 전체가 여기서 처음 등장. 24/7 수집 인프라 비용·운영 |
| 3 Correlation | Geo/Temporal 클러스터링 + Related Events | 3주 | 4~5주 | "14 diverted flights" 같은 파생 이벤트 추론은 룰 기반으로 안 나옴 |
| 4 Advanced | Ship/Wildfire/Volcano/Lightning/AQ + Heatmap/Flow | 6주 | 8주+ | 레이어당 신규 API 계약·정규화·시각화 반복 |
| 5 AI | Summary / Correlation 설명 / Briefing | 3주 | 4주 | LLM 호출 자체는 쉬우나 입력 컨텍스트 구성(=Phase 3 품질)에 종속 |

**합계: 낙관 27주(≈7개월), 현실 36~44주(≈9~11개월), 데모 폴리시·배포·문서까지 포함하면 12~14개월.** 풀타임 전환 시 4~5개월. 사이드 프로젝트가 6개월을 넘기면 완주율이 급락한다는 점에서, 이 계획은 "그대로 실행하면 Phase 2 어딘가에서 방치된 리포지토리가 될" 전형적 형태다.

## 2. '여기서 멈춰도 완성' 경계선

**제안 경계선: Phase 0 + 축소 Phase 1 + "지진 한정 Time Machine" = 약 12~16주(3~4개월).**

구성:
1. 3D Globe + **지진(USGS) + 항공기(OpenSky) 라이브** — Phase 0 그대로.
2. Event Detail + Layer Toggle + URL State — Phase 1에서 유지.
3. **Timeline/Replay는 지진 레이어만, USGS 과거 조회 API로 구현.** 핵심 통찰: USGS는 과거 지진을 쿼리 API로 그대로 제공하므로 **자체 백엔드·저장소 없이** "2시간 전으로 이동 → Play" 데모가 가능하다. 항공기 리플레이는 세션 내 링버퍼(브라우저 메모리, 최근 30~60분)로 한정.
4. 뉴스는 자체 지오코딩 대신 **GDELT(이미 lat/lng 포함된 이벤트 제공)** 어댑터 하나로 대체 — "이질적 소스 3종 정규화" 주장 확보.

이 경계선에서 멈추면: 지구본 위 라이브 데이터 + 시간축 이동 + 멀티소스 정규화가 모두 시연되고, 백엔드 운영 부담이 0이라 **포트폴리오 사이트가 영구히 살아 있다**(정적 배포 + 클라이언트 fetch). 채용 담당자 관점에서 "완성된 제품"으로 보이는 최소 단위가 정확히 여기다.

Phase 2(자체 수집·저장) 이후는 "완성 후 확장"이지 완성 조건이 아니다.

| **전 지구 날씨 오버레이** (기온/강수/풍속 래스터) | **축소** | 경보(alerts) + 태풍 경로만. 래스터 타일 오버레이는 노력 대비 데모 효과 낮고, 글로벌 경보 통합 소스도 없음(NWS는 미국 한정) |

| **"14 diverted flights" 류 파생 추론** (섹션 7, 10) | **삭제 또는 하드코딩 케이스 스터디로 대체** | 항공기 우회를 실시간 추론하려면 비행계획 대비 이탈 감지 필요 — 룰 300km/60min으로 절대 안 나옴 |
| **WebSocket/SSE 실시간 게이트웨이** (Phase 2 이전) | **연기** | 지진은 분 단위, 항공기는 10~30초 폴링으로 데모 체감 차이 없음. 백엔드 없는 경계선 유지가 우선 |

### 데모 시나리오 6단계 — '보여주기 효과 대비 구현 난이도' 최악 순위

| 순위(나쁨→좋음) | 단계 | 판정 |
|---|---|---|
| 1 (최악) | **3. 태풍 선택 → 관련 항공편·뉴스** | 태풍 데이터 + 우회 항공편 추론 + 상관관계 3중 난제. 효과는 크지만 난이도가 압도적. 태풍은 계절 의존이라 데모 시점에 존재 보장도 안 됨 |
| 2 | **6. Event Cluster → 소스 간 연결** | 룰 기반으로 가능하나 "그럴듯한 클러스터"가 나오려면 데이터 품질·튜닝 비용 큼. 잘못 묶이면 오히려 신뢰 깎음 |
| 3 | **5. Play 재생** | 4번이 되면 증분이지만, 전 레이어 동기 재생은 항공기 스냅숏 저장 없이 불가 |
| 4 | **4. 2시간 전 이동** | 지진 한정이면 쉬움(USGS API), 전 레이어면 백엔드 필요 — 범위 정의에 따라 난이도 3배 차이 |
| 5 | **2. 일본 확대 → 4레이어 확인** | 뉴스·날씨 레이어 존재에만 종속. GDELT + 경보로 축소하면 무난 |
| 6 (최선) | **1. 접속 → 라이브 지구** | 난이도 최저, 첫인상 효과 최대. 여기에 폴리시를 몰빵해야 함 |

## 4. Phase 순서 위반 목록

1. **[치명] 백엔드·데이터 수집이 어느 Phase에도 배정 안 됨.** 섹션 17~20이 파이프라인·저장·Geo Index를 설계하지만, 섹션 25~30의 어떤 Phase에도 "Collector/Storage 구축"이 없다. Phase 2가 "Historical Data"를 요구하는 순간 암묵적으로 등장하는데, **항공기 스냅숏은 수집 시작 전 과거가 존재하지 않으므로** 전 레이어 리플레이를 원한다면 수집은 Phase 0~1부터 돌아야 한다. 계획서에 이 종속성 반영 안 됨. (지진·뉴스는 소스가 과거 조회를 제공하므로 예외 — 이 비대칭 자체가 계획서에 없음.)
2. **Timeline이 Phase 1과 2에 걸쳐 중복.** Phase 1 "Timeline" vs Phase 2 "Timeline Seek/Playback". 섹션 8은 -24h 범위를 기본이라 하는데 -24h는 이미 과거 데이터 = Phase 2 영역. 경계 제안: **Phase 1 Timeline = 라이브 + 세션 내 버퍼(클라이언트 메모리, 최근 30~60분) UI 골격**, **Phase 2 = 소스/서버 기반 과거 조회 + Seek + Replay**. 이렇게 자르면 -24h 약속은 Phase 2로 이동해야 함.
3. **Event Detail의 "Nearby Events"(섹션 7)가 Phase 1 산출물인데 상관관계는 Phase 3.** Phase 1 Detail 패널이 이미 "Weather Typhoon Warning / Flights 14 diverted"를 보여주므로 Phase 3 기능을 선취하고 있음. Phase 1 Detail은 단일 이벤트 속성만, Nearby는 Phase 3로 명시 이동 필요.
4. **URL State의 `time` 파라미터(섹션 24)가 Phase 1 배정인데 시간 이동은 Phase 2.** Phase 1에서는 `time` 파라미터가 무의미하거나 죽은 파라미터가 됨. 사소하지만 경계 불명확의 증상.
5. **Globe 엔진 결정(섹션 14)이 '검토' 상태로 열려 있음.** MapLibre+deck.gl vs Cesium은 이후 모든 렌더링·LOD·성능 작업의 전제. Phase 0 완료 조건에 "엔진 확정"이 명시돼야 하는데 없음. (참고: deck.gl globe view는 아직 experimental, MapLibre는 v5부터 globe projection 지원 — '진짜 3D 지구본' 요구 수준을 Phase 0에서 검증하고 잠가야 함.)
6. Phase 순서 자체(0→1→2→3→4→5)는 논리적으로 타당. 문제는 순서가 아니라 **각 Phase에 안 담긴 것들**(수집 시작 시점, 배포 시점)이다.

### Phase 0 완료 조건 개선안
현재: "3D Earth에서 지진+항공기 동시 표시 가능" — 검증 불가능한 서술.
제안:
- [ ] Globe 엔진 확정(선택 근거 1페이지 기록)
- [ ] 실 API 데이터로 지진 전건 + 항공기 5,000대 이상 동시 렌더, 중급 노트북에서 **팬/줌 중 30fps 이상**
- [ ] 항공기 위치 30초 이내 주기 갱신 확인
- [ ] 마커 클릭 → 원시 속성 표시
- [ ] **공개 URL로 배포됨** (첫 주부터 배포가 습관이어야 포트폴리오가 죽지 않음)

## 6. 포트폴리오 주장별 달성 기준 (섹션 32 심사)

| 주장 | 판정 | 주장 가능 기준 |
|---|---|---|
| Massive Data Rendering "수만~수십만" | **현재 과장.** 라이브 데이터는 항공기 ~1만 + 지진 수백 = '수만' 하한 겨우 | 실측 벤치마크 공개: **50,000+ 포인트 팬/줌 중 60fps(또는 100k@30fps), 측정 환경 명시.** 라이브만으로 부족하면 과거 7일 지진 + 항공 궤적 히스토리로 채워서 실데이터로 달성. 벤치 없이 이 문구 쓰면 면접에서 "몇 개까지 해봤어요?" 한 방에 무너짐 |
| Spatial Data Processing | 조건부 | 클라이언트 haversine 루프면 주장 불가. **H3 또는 PostGIS 실사용 + 반경 쿼리 p95 지연 수치** 제시 |
| Temporal Data Processing | 조건부 | 소스 API 프록시만으론 약함. **자체 수집 데이터 최소 7일 보존 + 임의 시점 복원** 시연 가능해야. (경계선 버전에서는 "USGS 위임 + 항공기 세션 버퍼"라고 정직하게 축소 서술 권장) |
| Realtime Architecture | **현재 과장 위험** | 폴링이면 'Realtime Architecture' 아님. WebSocket/SSE 푸시 + 재접속/백오프 처리까지 있어야 주장 가능. 없으면 문구를 'Live Data Integration'으로 낮출 것 |
| Worker Architecture | 조건부 | Worker 존재만으론 부족. **before/after 메인 스레드 프로파일(긴 태스크 제거 증빙)** 1장이면 충분히 강한 주장이 됨 |
| GPU Rendering | 약함 | deck.gl 기본 레이어 사용은 라이브러리 사용이지 GPU 프로그래밍이 아님. 커스텀 레이어/셰이더 1개(예: 지진 펄스 셰이더) 또는 DOM 대비 성능 비교 문서가 있어야 차별화 |
| Data Normalization | **가장 달성 쉽고 방어 가능** | 이질적 소스 3종 이상 → 단일 WorldEvent + 어댑터 인터페이스 + **어댑터 단위 테스트**. 경계선 버전에서도 확보됨 |
| Complex UI State | 조건부 | URL 하나로 전체 상태(위치+시간+레이어+선택) 복원 시연 + 레이어 간 시간 동기화 설명 가능해야 |

### 진짜 차별점과 최소 노력 증명법
'지도에 점 찍기'와의 차별점은 레이어 수도 3D도 아니고 **① 시간축(과거 복원·재생) ② 소스 간 상관(서로 다른 데이터가 한 사건으로 묶임)** 둘뿐이다. 최소 노력 증명법: **실제 발생했던 사건 1건(예: 특정 규모 7급 지진)의 '케이스 스터디 퍼머링크'를 만들어라.** URL State가 이미 있으므로 `?time=...&lat=...` 링크 하나 + README 상단 GIF로 "재생 버튼 → 지진 발생 → 여진 확산 → 뉴스 증가"를 30초 안에 보여주면, 라이브 태풍을 기다릴 필요 없이 차별점 2개가 동시에 증명된다. 비용은 거의 0(이미 만든 기능의 큐레이션).

### 'DevTools for Earth' 슬로건 판정
**현재 계획 기준 절반 과장.** DevTools의 본질은 타임라인 스크러빙 + 개별 이벤트 inspect + 로그 스트림인데, 계획에는 앞 둘만 있고 '이벤트 로그 패널'(Network 탭처럼 흘러가는 이벤트 리스트)이 없다. 역설적으로 이 패널은 구현이 싸고(리스트 렌더링) 슬로건을 완성시키며 접근성 대체 뷰(누락 #6)까지 겸한다 — 추가를 강력 권장. Phase 2(시간 이동)까지 완성되면 슬로건은 방어 가능, Phase 1에서 멈추면 'Live Map of Earth' 수준으로 낮춰야 정직하다.

## 7. 추가 권고

1. **이벤트 로그 패널 추가** — 위 서술대로 슬로건 완성 + 접근성 + 저비용. 계획서에 없는 기능 중 ROI 최고.
2. **케이스 스터디 퍼머링크 3건** — 데모가 라이브 데이터 상태에 인질로 잡히지 않게 하는 보험이자 README 헤드라인 콘텐츠.
3. **첫 주부터 배포** — Vercel/Cloudflare Pages에 Phase 0 프로토타입부터 올리고 매 Phase마다 URL이 갱신되게. "완성 후 배포" 계획은 사이드 프로젝트의 무덤.
4. **API 조사 스파이크를 Phase 0 앞에 1주 배치** — OpenSky 크레딧 정책, 타일 제공자 무료 한도, GDELT 스키마를 실측으로 확인하고 소스별 폴백(예: 항공기 데이터 불가 시 시드 스냅숏)을 문서화.
5. **데모 영상(90초) + README 아키텍처 다이어그램을 '기능'으로 백로그에 등록** — 문서화는 남는 시간에 하는 게 아니라 Phase 산출물이어야 함.
6. **디자인 방향 1페이지 선행 확정** — 다크 계기판/管制室 무드, 모노스페이스 수치 타이포, 시맨틱 컬러(지진=주황 계열, 경보=적색 등) 정도만 정해도 결과물 인상이 달라짐. frontend 룰(anti-template) 기준으로도 현재 계획은 방향 부재 상태.
